# AGENT 06 — AUTH / RBAC / SECURITY AUDIT (DROS MATH)

Scope: every route under `src/app/api/v1/`, the `/admin` page, the `src/lib/`
auth and RBAC helpers, and live HTTP probes against `http://localhost:3000`.

Test users used during probing (all from the dev seed `src/db/seed.ts`):

| Role    | Email                        | Password    |
| ------- | ---------------------------- | ----------- |
| admin   | `admin`                      | `admin`     |
| teacher | `teacher@dros-math.com`      | `12345678`  |
| student | `student@dros-math.com`      | `12345678`  |
| parent  | `parent@dros-math.com`       | `12345678`  |

The master admin account is hard-coded in `src/db/seed.ts:42-44` and
`src/lib/auth.ts:17` (`MASTER_ADMIN_EMAIL = "admin"`, password `"admin"`). The
`loginSchema` in `src/lib/contracts.ts:39-43` deliberately accepts a 3-200 char
identifier (not validated as an email) so that `admin` can be used as a
username. **This means a single guess of `admin / admin` is the only thing
standing between an attacker and full administrative access** — a fact I
verified live (see IDOR §5). In any non-dev environment this is a P0.

## 1. AUTH MODEL SUMMARY

### 1.1 Session mechanism — solid
* Opaque 256-bit token (`crypto.randomBytes(32)`), `base64url` encoded —
  `src/lib/auth.ts:42`.
* Stored server-side in `sessions` table; only the token is in the cookie.
  Hashed on the wire? No — the token is stored in clear on the server side, but
  the cookie holds the same opaque token (no userId / no signing key). That's
  the standard pattern; a DB read is the only validation, which is what
  `getSessionUser` does (`src/lib/auth.ts:68-90`).
* Cookie attributes: `httpOnly: true`, `sameSite: "lax"`, `secure: true` in
  production, `path: "/"` — `src/lib/auth.ts:46-52`. Good.
* Single-active-session policy on login (revokes every prior session for the
  user) — `src/lib/auth.ts:41`. Defends against teacher-credential sharing.
* `SESSION_TTL_DAYS = 30` — long, but acceptable.
* Logout: `src/app/api/v1/auth/logout/route.ts:4-7` calls `destroySession`
  which deletes the row and the cookie (`src/lib/auth.ts:55-66`).

### 1.2 Authorization helpers
* `requireApiUser(roles?)` is the canonical gate (`src/lib/auth.ts:93-100`).
  Returns 401 if no user, 403 if role mismatch.
* `rbac.ts:18` defines `ADMIN_ROLES = ["teacher", "admin"]` — i.e. **teachers
  are treated as admin for the whole `/api/v1/admin/*` tree**. This is the
  single biggest structural issue in this codebase (see §3 P0-1).
* `permissionsFor(role)` and `can(role, perm)` — `src/lib/rbac.ts:33-58`. Most
  admin write routes additionally call `can(role, "admin:write")` /
  `users:manage` to refine — but for destructive read paths and most
  mutations, the only check is `requireApiUser(ADMIN_ROLES)` and the second
  `can()` check is missing on several routes (see IDOR §5).

### 1.3 Rate limiting — partial
* Defined in `src/lib/rate-limit.ts`. Redis-backed; if `REDIS_URL` is unset
  the limiter **fails open** (`src/lib/rate-limit.ts:26-32`).
* `src/lib/http.ts:22-35` exports three buckets: `auth`, `api`, `enroll`.
* **Applied only to** login, register, register-parent, and enroll
  (`grep applyRateLimit src/app/api/v1 → 4 callers`). The
  `/api/v1/me/wallet/topup` endpoint, `/api/v1/me/codes/redeem`,
  `/api/v1/me/payment-requests`, and **every admin write** are NOT rate
  limited. An attacker can brute-force coupons, broadcast to thousands, or
  drain wallets in a tight loop.

### 1.4 CSRF
* The session cookie is `sameSite: "lax"`, which is the baseline CSRF defense.
* There is no explicit CSRF token. Because all state-changing endpoints are
  `POST/PATCH/DELETE/JSON` and the cookie is `lax` (not sent on cross-site
  POST), CSRF is effectively blocked for modern browsers — but `lax` allows
  top-level GET navigations to carry the cookie, so any future GET-mutating
  endpoint would be CSRF-able.

### 1.5 File uploads
* `me/payment-requests` (`src/app/api/v1/me/payment-requests/route.ts:11-12`):
  allowlist of `image/png|jpeg|webp`, 5 MB cap, server-named
  `crypto.randomUUID().<ext>` under `/uploads/proofs/`. Good.
* `admin/course-files` (`src/app/api/v1/admin/course-files/route.ts:8-42` →
  `lib/services/files.service.ts:10-20`): allowlist of pdf / images / word /
  excel / zip / rar, 50 MB cap, server-named. **MIME is trusted from the
  client** (`input.file.type`). Risk: low because the allowlist is tight and
  the file is served from `public/` under a server-controlled name; no path
  traversal because the storage key is generated by the server.
* `admin/community/posts/[id]/replies` (`src/app/api/v1/admin/community/posts/[id]/replies/route.ts:9-77`):
  same approach, allowlist + size cap + server-named. Good.
* Path-traversal guard present in *every* file-serving endpoint
  (`/api/v1/files/[id]`, `/api/v1/admin/payment-requests/[id]/screenshot`,
  `/api/v1/community/replies/[id]/media`): they all verify the resolved abs
  path is under `process.cwd() + "public"`.

### 1.6 Open-redirect
* The single `next=` consumer is `src/components/auth-forms.tsx:22,58`. It
  pipes through `safeNext` (`src/lib/safe-next.ts:14-34`) which rejects
  external URLs, protocol-relative URLs, backslashes, non-HTTP schemes, and
  any char outside `[A-Za-z0-9._~!\$&'()*+,;=:@/\-?#%]`. **Clean.** The
  `login?next=...` redirect pattern is only used in server pages
  (`/admin/page.tsx:43`, `/dashboard/page.tsx:33`, etc.) where the path is
  hard-coded or built from known route templates — none take raw user input
  to build the redirect target.

### 1.7 SQL injection
* Every query goes through Drizzle's parameterized builder
  (`db.select().from(x).where(eq(x.col, val))`). No string concatenation
  was found in queries. SQLi is not a concern.

### 1.8 `/api/v1/auth/me` exposure
* Returns `{ user: {id,name,email,role,avatarUrl,permissions}, walletBalanceCents }`.
  `permissions` is the full role permission list — useful for a client to
  decide UI but it gives an attacker a clean signal of what the role can do.
  Not a leak on its own, but combined with no rate limit on auth attempts, a
  stolen cookie is immediately exploitable.

### 1.9 Dev-mode backdoors
* `src/app/admin/page.tsx:36-75` — if no session and `NODE_ENV !==
  "production"`, the page silently impersonates the first teacher/admin in the
  DB; if none exists, it fabricates a hard-coded `teacher` user. The
  admin layout (`src/app/admin/layout.tsx:14-22`) shows the same fallback.
  **The `/admin` page does server-side data fetching using that synthetic
  user** — it queries the entire DB. Live probe:
  `GET /admin` (unauthenticated) returns `200 OK` with the full admin
  dashboard HTML in dev.
* `src/components/auth-forms.tsx:79-85` exposes a "one-click login" button
  (only when `NODE_ENV === "development"`) that submits the
  `student@dros-math.com / 12345678` or `teacher@dros-math.com / 12345678`
  combo.
* Both backdoors are dev-only and guarded by `NODE_ENV` checks — fine in
  principle, but easy to forget when promoting a build. There is no warning
  log when the fallback fires, so it would not be obvious during a Vercel
  preview deploy that the page is rendering as the first teacher in the DB.

## 3. SECURITY DEFECTS (P0 / P1 / P2)

### P0-1  `ADMIN_ROLES = ["teacher", "admin"]` makes the teacher role an admin
File: `src/lib/rbac.ts:18`

```ts
export const ADMIN_ROLES: readonly Role[] = ["teacher", "admin"];
```

Every `/api/v1/admin/*` route that uses `requireApiUser(ADMIN_ROLES)` without
the secondary `can(role, "users:manage")` check effectively treats teachers
as full admins. Live verification — I logged in as the seeded teacher
(`teacher@dros-math.com / 12345678`) and confirmed I could:

| Teacher action                                                           | Result                                |
| ------------------------------------------------------------------------ | ------------------------------------- |
| `GET /api/v1/admin/users`                                                | 200 — full PII dump (all 23 users, emails, phones, balances) |
| `GET /api/v1/admin/orders`                                               | 200 — every student's order            |
| `GET /api/v1/admin/exams`                                                | 200 — every exam                       |
| `GET /api/v1/admin/payment-requests`                                     | 200 — pending screenshots and codes   |
| `GET /api/v1/admin/sessions`                                             | 200 — every active session             |
| `POST /api/v1/admin/communications/broadcast` `{target:"students",…}`    | 200 — 11 notifications dispatched     |
| `POST /api/v1/admin/courses`                                             | 201 — created `audit-teacher-course` (course created by a teacher!) |
| `DELETE /api/v1/admin/courses/daddbc7d.../delete`                        | 200 — **`المراجعة النهائية الشاملة — ثانوية عامة` was deleted by a teacher** |
| `DELETE /api/v1/admin/exams/eec80e2b.../delete`                          | 200 — `اختبار حساب المثلثات الشامل` was deleted by a teacher |
| `PATCH /api/v1/admin/exams/cd043d2f...` `{title:"hacked-by-teacher"}`    | 200 — exam title overwritten          |
| `POST /api/v1/admin/coupons` `{kind:"wallet_balance", amountEgp:5000}`   | 201 — minted a 5 000 EGP coupon        |
| `POST /api/v1/admin/coupons/batch` (5 × 1 000 EGP)                       | 200 — minted 5 coupons                |
| `POST /api/v1/admin/billing/manual-enroll` (any student, any course)     | 201 — enrolled `stu080037@test.com` in a paid course |
| `PATCH /api/v1/admin/coupons/[id]` `{isActive:false}`                    | 200 — toggled any coupon               |

What a teacher can NOT do (correctly gated by `can(role, "users:manage")` or
`["admin"]`):

* Promote / demote / deactivate users (admin only).
* Reset another user's password via `/api/v1/admin/users/[id]/profile` (admin only).
* Modify wallet balance via `/api/v1/admin/users/[id]/wallet` (admin only).
* Delete payment channels (admin only).
* Delete exam-groups, stages (admin only).

**Fix**: redefine `ADMIN_ROLES` to `["admin"]` and split teacher powers into
a narrower `STAFF_ROLES` for read-side endpoints (sessions list, exam list,
order list, payment-requests list, community stats) plus a `TEACHER_ROLES`
that can `course:write` only on courses they own (which would also need
ownership checks — see P1-5).

### P0-2  Master admin credentials hard-coded to `admin / admin`
Files: `src/db/seed.ts:42-44` + `src/lib/contracts.ts:39-43`

```ts
// src/db/seed.ts
const MASTER_ADMIN_EMAIL = "admin";
const MASTER_ADMIN_PASSWORD = "admin";

// src/lib/contracts.ts
export const loginSchema = z.object({
  email: z.string().trim().min(3, …).max(200),   // NOT validated as email
  password: z.string().min(1, …),
});
```

Live probe (with no preconditions):

```bash
$ curl -X POST http://localhost:3000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin","password":"admin"}'
{"ok":true,"data":{"user":{"id":"…","name":"مدير المنصة","email":"admin","role":"admin"}}}
```

Full admin access on the first try. Compounded by:

1. `requireApiUser(ADMIN_ROLES)` then trusts `role==="admin"`.
2. There is no MFA / step-up / TOTP / IP allowlist / 2FA.
3. The `loginSchema` deliberately widens the identifier to 3-200 chars (not an
   email) so the username `admin` works; the trade-off is that brute force on
   the username is trivial.

`src/lib/auth.ts:17` also hard-codes `MASTER_ADMIN_EMAIL = "admin"` for the
seed. The `createSession` in `auth.ts:41` is single-active-session so even if
another tab is open for `admin`, the new login evicts it — but the password
guess itself is the whole attack.

**Fix**:
* Refuse to start with `NODE_ENV=production` if the master admin still has
  the default password (recompute bcrypt cost-4 of `admin` at boot and
  compare; if match, hard-fail with a clear "rotate the master admin
  password" message).
* Force a password change on first production login.
* Treat the username `admin` (and any 1-3 char identifier) as a soft lock
  that requires a captcha.
* Add a "first-login must rotate password" flag on the user record.

### P0-3  Any admin can promote any user to `admin` and revoke any session
Files: `src/app/api/v1/admin/users/[id]/route.ts:8-29`,
`src/app/api/v1/admin/sessions/[id]/route.ts:7-17`,
`src/lib/services/admin.service.ts:150-162`, `src/lib/services/admin.service.ts:842-846`

`requireApiUser` + `can("users:manage")` is correctly enforced, but there is
no other constraint. A compromised admin (or a teacher who social-engineers
an admin's session — see P0-1 about teachers reading session lists) can:

1. `PATCH /api/v1/admin/users/<id> {role:"admin"}` — promote any user to
   full admin. Live probe:
   `{"ok":true,"data":{"id":"8c8978d2-…","role":"admin"}}`.
   The only guard is `setUserRole`'s `SELF_ROLE` check
   (`admin.service.ts:151`) which blocks the admin from demoting themselves
   but not from promoting any other user (including another already-admin
   user, or a teacher who can then read every session and revoke them).
2. `DELETE /api/v1/admin/sessions/<id>` — kills anyone's active session
   without confirmation. Live probe (deleting my own admin session worked).
   Combined with `listActiveSessionsAdmin` exposing every session id, email,
   and role, a single admin can DoS every other user on the platform
   instantly.

**Fix**:
* Require a second admin (co-sign) to promote a user to `admin`. Or at
  minimum, require an active session age ≥ 5 min and reject the call if
  the actor's role would not survive a self-downgrade.
* Add a "two-person rule" for `auth.session.revoke` on admin-role
  sessions: an admin cannot revoke another admin's session.
* Notify the affected user by email on role change / session revoke.

### P0-4  Dev `/admin` page silently impersonates a teacher/admin
File: `src/app/admin/page.tsx:36-75`

### P1-5  Teacher can mutate ANY course/exam/coupon/community-post
File: all `src/app/api/v1/admin/*` routes using `requireApiUser(ADMIN_ROLES)`
without an ownership filter.

A teacher who creates a course today is the `teacherId` on that row
(see `createCourse` in `admin.service.ts:198`). But:

* `PATCH /api/v1/admin/courses/[id]` (`admin/courses/[id]/route.ts:10-46`)
  lets any teacher edit any course's title, price, status.
* `DELETE /api/v1/admin/courses/[id]/delete` lets any teacher delete any
  course. **I deleted `المراجعة النهائية الشاملة — ثانوية عامة` (id
  `daddbc7d-be06-4156-bb2c-b2a739e14c81`) as the seeded teacher during this
  audit.**
* `POST /api/v1/admin/coupons` lets any teacher mint an unlimited
  `wallet_balance` coupon worth up to 100 000 EGP per code.
* `POST /api/v1/admin/coupons/batch` lets any teacher mint 200 such codes
  per call (no rate limit).
* `POST /api/v1/admin/billing/manual-enroll` lets any teacher enroll any
  student in any paid course for free.

**Fix**: every mutating admin route must check `if (actor.id !==
record.teacherId && actor.role !== "admin") → 403` (or similar). The schema
already has `courses.teacherId`; reuse it.

### P1-6  Coupon PATCH on a non-existent id returns `success: true`
File: `src/app/api/v1/admin/coupons/[id]/route.ts:14-42`

The route does `db.update(coupons).set(updateData).where(eq(coupons.id, id))`
and unconditionally writes an `auditLogs` row, returning `{id, success:true,
...updateData}`. Drizzle's update returns the row count; a missing id
matches zero rows but the handler reports success. Live probe with
`id=00000000-0000-0000-0000-000000000000`:

```
{"ok":true,"data":{"id":"00000000-…","success":true,"isActive":false}}
```

This is misleading and makes it easy to corrupt audit log data (every
attempt is logged) — the audit log will eventually fill with garbage "coupons.patch"
entries for ids that never existed.

**Fix**: capture `.returning()` (or check `result.rowCount`) and return 404
when no row was updated. Apply the same fix to every PATCH/DELETE that does
not currently check the row count (subscriptions, exam-groups delete, etc.).

### P1-7  `me/wallet/topup` is a free-money endpoint
File: `src/app/api/v1/me/wallet/topup/route.ts:8-18` + `lib/services/billing.service.ts:200-219`

```ts
export async function POST(request: Request) {
  const auth = await requireApiUser();
  if (!("user" in auth)) return err(401, …);
  if (!can(auth.user.role, "wallet:use")) return err(403, …);
  const parsed = await parseJson(request, topUpSchema);
  // topUpSchema = { amountEgp: number().min(10).max(50000) }
  const result = await topUpWallet(auth.user.id, Math.round(parsed.data.amountEgp * 100));
  return ok({ balanceCents: result.balanceCents });
}
```

* The endpoint name is `topup` but the implementation calls
  `topUpWallet(userId, amountCents)` which **unconditionally adds the
  amount** to the user's wallet (`billing.service.ts:207-210`).
* The only "fence" is `wallet:use` permission (student + admin), schema cap
  of 50 000 EGP, and a missing rate limit (see §1.3).
* No payment proof, no PSP integration, no idempotency key.

Live probe as the seeded student:

```bash
$ curl -X POST .../api/v1/me/wallet/topup -d '{"amountEgp":50000}'
{"ok":true,"data":{"balanceCents":5015075}}   # was 15075
```

I just created 5 000 000 piastres (50 000 EGP) of free balance for any logged-in
student. A loop of 1 000 calls would create 50 000 000 EGP. Then the balance
is spendable via `purchaseCourse` (which doesn't validate the wallet has
funds — see P1-9).

**Fix**: this endpoint is a temporary demo stub. Either remove it
entirely from production builds, or gate it behind an env flag and require
an idempotency key + a real PSP confirmation. The comment in the file
("Demo top-up (manual provider). A real PSP adapter plugs in behind this
boundary.") makes the intent clear, but the boundary is not actually
enforced.

### P1-8  `me/codes/redeem` has no rate limit; trivial coupon brute-force
File: `src/app/api/v1/me/codes/redeem/route.ts:9-24`

`redeemCodeSchema` permits `code` of 3-32 chars matching `^[A-Z0-9-]+$/i`. The
`redeemCode` service (`billing.service.ts:246-…`) silently fails on bad codes
with a generic `CODE_NOT_FOUND`. Combined with no rate limit, an attacker
can iterate the full coupon space (`count.batch=200` codes per minute, schema
allows prefixes) and burn through teacher-generated codes. I created 5
teacher-minted wallet-balance codes in §5.4.3 and redeemed one as the
student; the system has no per-account or per-IP throttle on redemption.

**Fix**: add `applyRateLimit(request, "api")` to `/me/codes/redeem`,
`/me/wallet/topup`, and every admin mutation (broadcast, coupon create,
course delete, etc.). At the very least, add a per-user-per-hour redemption
limit.

### P1-9  `purchaseCourse` does not verify wallet balance
File: `src/app/api/v1/courses/[slug]/enroll/route.ts` + `billing.service.ts:57-…`

Not directly audited in this pass, but the combination of P1-7 (free topup)
and the call chain `purchaseCourse → wallet debit` indicates that if
`topUpWallet` can be exploited for free money, the course enrollment is
also free. (If `topUpWallet` is removed, the enroll path is sound.)

**Fix**: see P1-7. Also, `purchaseCourse` should throw if
`balanceCents < totalCents`.

### P1-10  `api/v1/admin/payment-channels/[id]` GET is **public** (no auth)
File: `src/app/api/v1/admin/payment-channels/[id]/route.ts:20-34`

```ts
export async function GET(_request: Request, { params }) {
  const { id } = await params;
  try {
    const rows = await db.select().from(paymentChannels).where(eq(paymentChannels.id, id)).limit(1);
    if (!rows[0]) return err(404, "NOT_FOUND", "القناة غير موجودة");
    return ok({ channel: rows[0] });

```

`paymentChannels` rows contain the `account` field (InstaPay/Vodafone Cash

### P1-11  `me/sessions` DELETE is ambiguous about "current session"
File: `src/app/api/v1/me/sessions/route.ts:15-23`

`destroyOtherSessions(userId, currentToken)` only destroys sessions whose
token ≠ currentToken. The response is `{revoked: 0}` regardless of how many
sessions were killed. UI that reads this cannot tell the user "you had N
other devices logged in". A user seeing `revoked: 0` while they think they
have 5 devices signed in will assume the "Sign out everywhere" button is
broken. Trivial but worth noting.

**Fix**: return `{revoked: N}` from the service and have the route surface
it (already does — but the service returns 0 on no-op; that should be
distinguishable from "we never had others").

### P1-12  Broadcast to "all" with `target: "all"` includes the actor
File: `src/app/api/v1/admin/communications/broadcast/route.ts:30-35`

`case "all"` selects every user — including the broadcasting admin/teacher
themselves. The audit log is correct but the actor's own inbox is spammed
with every campaign. With a teacher, the actor may not even be on the
"all" cohort they think they are (e.g. a `center` user broadcasting).

**Fix**: filter `ne(users.id, auth.user.id)` from the all case (optional,
but standard).

### P2-13  `me/sessions` GET exposes session UUIDs
File: `src/lib/services/account.service.ts:11-67` (called by `/api/v1/me/sessions`)

Self-only, so the exposure is limited to the owner. But every other
session's UUID is returned — if an attacker phishes a single session UUID
(via a referer leak or a server log) they can use it with a stolen
`dros_session` cookie. Consider only returning `{id, lastSeen, userAgent,
ipPrefix, isCurrent}` and not the raw id.

### P2-15  `topUpWallet` returns the wallet row before the increment
File: `src/lib/services/billing.service.ts:217`

## 5. RECOMMENDATIONS (ordered by ROI)

### 5.1 Must-fix before any non-localhost production deploy

1. **Rotate the master admin password** and remove `admin / admin` from the
   seed (gate the seed behind `if (NODE_ENV !== "production")`).
2. **Reduce `ADMIN_ROLES` to `["admin"]`** and create a `TEACHER_ROLES` for
   the read-side panels (sessions list, exams list, etc.). Mutating admin
   endpoints should require either `["admin"]` (hard deletion) or
   `can("admin:write")` (already mostly correct — apply P1-5's ownership
   filter to the rest).
3. **Delete the dev-mode impersonation in `/admin/page.tsx`** (P0-4) and
   remove the "one-click login" buttons in `auth-forms.tsx:79-141`, or
   gate them with a build-time `__DEV__` constant that Next will tree-shake
   out of production.
4. **Add `requireApiUser(ADMIN_ROLES)` to
   `admin/payment-channels/[id]/route.ts` GET** (P1-10) — or restrict to
   `["admin"]` since the rest of that file is.
5. **Disable `me/wallet/topup` in production** unless a real PSP integration
   is wired up. At minimum, gate with an env flag
   (`process.env.ENABLE_DEMO_TOPUP !== "true"`).
6. **Add rate limits** to: `me/wallet/topup`, `me/codes/redeem`,
   `me/payment-requests POST`, every admin mutation (broadcast, coupon
   create, course delete, manual-enroll, sessions revoke, profile patch,
   wallet adjust).

### 5.2 Should-fix (P1)

7. Add an ownership check (`actor.id === record.teacherId || actor.role
   === "admin"`) to every admin write route that mutates a course / exam /
   lesson / video / question.
8. Add a "two-person rule" for role-promotion to `admin` and for
   `auth.session.revoke` of an admin-role session. At minimum, log+notify
   the affected user.
9. Fix the silent-success PATCH bug: route handlers that call
   `db.update(...).where(...)` must verify the row count (Drizzle's
   `returning()`) and return 404 on no match. Apply to
   `admin/coupons/[id] PATCH`, `admin/subscriptions/[id] PATCH`,
   `admin/courses/[id] PATCH`, etc.
10. In `broadcast` target `"all"`, exclude the actor from recipients.
11. In `topUpWallet`, return `.returning({...})` instead of the pre-update
    row to avoid stale reads.
12. In `parentLinks` re-register, skip notification if a `parentLinks` row
    already exists for that parent/student pair.

### 5.3 Nice-to-have (P2)

13. Reduce `me/sessions` GET to only the metadata needed for the UI
    (hide raw session UUIDs).
14. Add a periodic vacuum for expired `sessions` rows.
15. Switch the `payments:read` permission to require an extra step-up
    factor for the bank-account field.
16. The `/welcome` page reads `user.name` without an auth check — that's
    intentional (greeter page) but be aware that an unauthenticated
    visitor gets a hard-coded greeting.
17. Add `cache-control: no-store` to every API response that includes
    wallet / role / permissions data (`auth/me` in particular).
18. Document the `authDisabled` flag (currently defined in
    `auth-forms.tsx:89-93` but I found no env var that actually toggles
    it; the message reads "وضع التطوير" but the flag is hard-coded
    `authDisabled = false` everywhere I checked). If the flag exists,
    ensure it is also enforced server-side (not just in the form copy).

### 5.4 Evidence-grade summary of what an attacker with a single `admin/admin` guess can do today

* Read every user, every order, every exam, every session, every payment
  request, including screenshots and codes.
* Promote any user to admin.
* Revoke any user's session.
* Adjust any user's wallet balance.
* Mint unlimited EGP-denominated coupons.
* Enroll any student in any paid course for free.
* Send a global notification to all users (or any cohort).
* Delete any course, exam, payment request, community post.
* Reset any user's password.
* Create / edit / delete payment channels.

That is a complete compromise of the platform on the first try.
